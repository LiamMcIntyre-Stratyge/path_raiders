<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (anon, signed-in) → wallet | Forged write must be denied by RLS — proven here |
| build output (dist/) → every client browser | A leaked privileged key would ship to all clients — scan is the backstop |
| PR/push → main | CI is the gate before deploy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-forged-write | Tampering / Elevation | client forging wallet.balance | mitigate | RLS test proves a forged UPDATE leaves the row unchanged (re-read as service-role, Pitfall 1) — gates CI |
| T-09-double-credit | Tampering | replayed credit | mitigate | idempotency test asserts same-key retry credits once |
| T-09-secret-bundled | Elevation of Privilege | service-role key shipped in dist/ | mitigate | `scripts/scan-bundle.sh` greps for `sb_secret_`/service_role markers, fails build; planted-secret negative test proves it catches a real key shape (A5) |
| T-09-test-key-leak | Elevation of Privilege | service-role key imported by src/ for the test | mitigate | RLS test reads SERVICE_ROLE only from `process.env` (CI env via `supabase status`), never from `src/`; scan also flags any `SUPABASE_SERVICE_ROLE_KEY` literal in the bundle |
| T-09-stale-stack | — | RLS test runs before migrations applied | mitigate | CI orders `supabase start` → `db reset` → export keys → `vitest --project rls` (Pitfall 5) |
| T-09-SC | Tampering | `supabase/setup-cli@v2` action / CLI download | mitigate | Pinned action `@v2` + `version: 2.106.0`; official Supabase action (not `npx supabase`) |
</threat_model>
